# Мерж PR и выкладка в портал

> Последняя сверка: 2026-10-17

Правила — [docs/private/agent-rules.md](../../../docs/private/agent-rules.md), §4; выкладка —
[docs/private/deploy.md](../../../docs/private/deploy.md). Этот навык — порядок действий.

## 1. Перед кнопкой — выполняется всё

1. **Свежий `main` влит**: `git fetch origin main && git merge origin/main`,
   `./build.sh --check`, пуш. Мерж чистый.
2. **CI зелёный** на последнем коммите — обязательная проверка одна, `CI`.
3. **Треды ревью закрыты** — на каждый ответ или правка. Ревью было по навыку
   `review-panel`.
4. **Версия и CHANGELOG**: поведение поменялось — `VERSION` и `VERSION_DATE`
   в `install/version.php` подняты, в `CHANGELOG.md` секция `## <версия> — <дата>`
   ([CONTRIBUTING.md](../../../CONTRIBUTING.md), «Версия и релиз»).
5. **Документация сверена с правкой.** Каждое изменённое поведение описано там,
   где его будут искать: `CLAUDE.md` (опорные точки, решения, ловушки),
   runbook, профильный документ в `docs/`, описание модуля для людей. В описании
   PR названо, какие разделы тронуты, — или почему не нужно ни одного.
   Штамп `> Последняя сверка:` в тронутых документах — на дату мержа.
6. **Отложенное — issue по-русски**: что, почему, где (`файл:строка`), как
   проверить, ссылка на PR. «Починить потом» одной строкой — не issue.
7. **Сообщение сквоша** пишется для человека, который через полгода спросит
   «почему так»: заголовок называет **решение**, а не файлы; тело — довод и
   цена: что измерено, что отвергнуто и почему. Ссылка на issue — `(#N)`.

Что-то не выполняется — не мержить и сказать, что именно.

## 2. Мерж

Только сквош. Агент мержит сам то, в чём уверен и что проверил
([CONTRIBUTING.md](../../../CONTRIBUTING.md), «Мерж»); остальное — по прямой
просьбе владельца.

## 3. После мержа

1. **Одна ветка на origin**: `git ls-remote --heads origin` — только `main`.
   Packagist делает `dev`-версию из каждой ветки. В слитую ветку не пушить.
2. **Issue закрыт этим PR — комментарий по-русски**: по-доброму и с лёгким
   юмором, пара примеров или ссылок на документацию (ссылки открыть), где к
   месту — пример промпта; спасибо от владельца. Закрыть issue, если решено.
3. **Карта проекта**: [docs/private/project-map.md](../../../docs/private/project-map.md) —
   сделанное перенести, «что в работе» и открытые вопросы обновить.
4. **Итог владельцу простыми словами**: что сделано, следующий шаг и что за
   ним; отдельно — что мешает.
5. **Выпуск с новой версией — тег.** После мержа PR, который поднял `VERSION` в `install/version.php`, ставим аннотированный тег `v<версия>` на squash-коммит в `main`: `git tag -a v<версия> -m "<заголовок squash-коммита>" <коммит>`, затем `git push origin v<версия>`. Тег с такой версией уже есть — не перезаписываем. Решение владельца от 2026-10-17.

## 4. Релиз и выкладка в портал — только по слову владельца

Выпуск релиза и изменение портала клиента — решения владельца; тег после мержа выпуска — п. 5 раздела 3 (agent-rules §5.8).
Порядок — [docs/private/deploy.md](../../../docs/private/deploy.md):

1. **Релиз**: Actions → Release → Run workflow от `main`; тег = `VERSION`.
2. **Ветка и issue в репозитории портала** — по его правилам (у портала свои
   CLAUDE.md, шаблоны issue и PR).
3. **Копия модуля**: каталог модуля в портале очистить и разложить
   `git archive <тег или коммит>` — export-ignore уберёт тесты и документацию,
   как у пакета Composer.
4. **Заглушки вне каталога модуля** — `/bitrix/admin/shef_toolsai_*.php`,
   `/bitrix/tools/shef_toolsai_completions.php` — ровно такие, какие пишет
   `Main\PublicPage::getContent()`. Новая страница в версии — новая заглушка.
5. **Версия портала** поднята, в документации портала — версия и коммит модуля.
6. **PR в портал**: что и зачем, версия модуля, ссылка на CHANGELOG, шаги после
   деплоя, откат. Мержит владелец портала; мерж запускает автодеплой.
7. **После деплоя**: **«Проверить и включить»** (новые таблицы и агенты), отчёт
   зелёный; `git status` на сервере чистый; проверки из deploy.md. Новые функции
   включает владелец — по runbook.
